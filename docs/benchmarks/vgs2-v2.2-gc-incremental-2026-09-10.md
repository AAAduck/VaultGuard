## 一、目标档（10,000 文件 / 5 GiB）同会话 A/B

同一会话内先跑 v2.2、后跑 v2.1 基线（`git stash` 切换后重新构建），各 3 次。
`save_s` 作为「非 GC 路径未受影响」的对照：两轮会话均为 23.7–27.1s，属同一水平
（本节基线轮略快），说明下面的 compact 差值不是环境漂移造成的。

| run | 基线 compact_s（全量重写） | v2.2 compact_s（增量段级 GC） |
| --- | --- | --- |
| 1 | 34.948 | 19.442 |
| 2 | 32.007 | 19.567 |
| 3 | 33.951 | 17.444 |
| **中位数** | **33.951** | **19.442** |

**→ 全量压缩 1.75×**（v2.2 比基线少 ~14.5s）。

同轮其它阶段（中位数，非闸门项）：

| 阶段 | 基线 | v2.2 | 说明 |
| --- | --- | --- | --- |
| manifest 打开（open_s） | 0.266s | 0.260s | 持平 |
| 首次保存（save_s） | 23.820s | 24.916s | 持平（未改保存路径） |
| 全量压缩（compact_s） | 33.951s | 19.442s | **1.75×** |

v2.2 段级统计（三次一致）：`gc_dead=0 gc_reuse=81 gc_segs=81`
—— 81 个数据段全部判定为「纯活段」并整段复用，无一走 tar 解包/重打包。

> 注：v2.1 记录（`vgs2-v2.1-parallel-2026-09-10.md`）中该档 compact 中位数为 25.898s。
> 本次会话整体 I/O 比当时的会话慢约 25%（对照 `save_s` 19.6s → 23.8s，代码未变），
> 因此跨会话比较不可靠；上表同会话 A/B 是本节唯一采用的结论依据。

## 四、本次改了什么

1. **复用密钥与全局头**：压缩不再重新派生主密钥（省一次 Argon2 ~0.16–0.25s），
   全局头逐字节复制；每段 nonce 重新随机取，(key, nonce) 无复用。
2. **免明文临时文件**：按内存额度给待处理段切波，一波内的段解密到内存
   （预算 `PARALLEL_BUF_BUDGET` = 512MiB，8 段 × 64MiB 段目标恰好用满），
   省掉原来的「写明文临时 tar → 读回 → 覆写擦除」三趟 I/O。
   单段本身就超预算（单个超大文件）时才退回临时文件 + 流式串行。
3. **纯活段整段复用**：段内**文件**条目全部仍在 manifest 里时，明文整段直接作为新
   数据段重加密，跳过 tar 解包 / 逐条目重打包（目录条目不计入判定：它们不携带数据，
   还原结构来自 manifest）。含已删除文件的「混合段」才做批转发重打包。
4. **全死段整段跳过**（沿用并保留语义）：没有任何存活条目引用的数据段不读、不解密、不写；
   旧 manifest 一并回收。
5. **崩溃回退语义不变**：新容器先写占位段头，tag 落盘后回填，全容器认证校验通过才原子替换旧箱
   （`MoveFileExW` 同卷覆盖）；段序号与物理顺序一致（写盘串行、加密并行）。
6. **顺带收益**：复用 / 内存路径不再产生明文临时文件，明文落盘面进一步缩小。

非 GC 路径（打开、首次保存、VGS1 升级）代码未动，A/B 中 `save_s`、`open_s` 持平。

## 五、未达成：真正的 O(单段)

路线里原写「可评估段级重写（O(单段)）」。结论：**在现有 VGS2 布局下不可达**，原因是两个硬约束叠加：

- **段序号必须与物理顺序连续**（扫描器要求 seq 从 1 连续递增，AAD 又把 seq 绑进认证），
  所以删除中间任意一段都要给它之后的**所有**段重新编号 → 必须重新加密；
- **崩溃安全要求「临时文件 + 原子替换」**（就地覆盖会让断电窗口内旧箱不可回退），
  于是活着的数据至少要经历一趟「读 + 写」的全量往返。

因此本轮落在「**不做无用功**」上：不重打包纯活段、不落明文临时文件、不重派生密钥。
要真正做到「任意位置删一个大文件只读写一个段」，需要引入 **tombstone（墓碑）段类型**
（标记为已回收但保留 seq 占位，扫描器跳过）——新增段类型属于格式变更，须按纪律走
「新头 + 旧格式可解 + 测试向量入库」，列为 v2.3 评估项，本轮不做。
