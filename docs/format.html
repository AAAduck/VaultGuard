VaultGuard 格式规范

容器格式的字节级说明。全部格式公开，任何人可据此独立实现解码器，也可自行构建程序比对产物哈希。

总则

  • 字节序：所有多字节整数一律大端（Big-Endian），无对齐填充。
  • 加密原语：AES-256-GCM，认证标记（tag）16 字节，常量时间比较；GHASH 使用 RustCrypto ghash。
  • 口令派生：Argon2id（m=64MiB, t=3, p=1），随机 16 字节盐。参数写入文件头，未来调整不影响旧文件解密。
  • 三类格式：单次加密产物（VG 系列，伪装成图片/文档）、历史保险箱（VGS1）、当前保险箱（VGS2，段链）。
  • 明文处理：加密侧 tar 流直通加密管道，明文不落盘；解密侧先认证后落位，临时明文用后覆写擦除。

VG 系列 —— 单次加密产物

一次加密一个文件或文件夹，产出单个自包含文件（伪装的 PNG / JPG / DOCX，或裸 .vaultguard）。

魔数用途密钥派生
VG\x03口令加密（推荐）Argon2id：m=64MiB, t=3, p=1 + 随机 16B 盐，盐与参数写入头部
VG\x02内置密钥（无口令）内置主密钥 + HKDF-SHA256；仅防随手翻看，不提供真实保密性
VG\x01旧版产物仅解密兼容；PBKDF2，600,000 次迭代

外壳数据藏匿位置
PNG私有块 vGDT

DOCXword/vaultData.bin（并拒绝超长记录，防恶意容器崩溃）

历史保险箱（VGS1，.vgsafe）

单段式：整箱作为一个 tar 流加密，任何修改都需要全量重写。

VGS2 — 当前保险箱格式 已接管读写

段链式：全局头 + 追加式相接的段。打开只认证 manifest，日常增删只追加段，面向"1 万文件、5GiB 级"资料库。

文件整体布局

[全局头 50B][段 1][段 2][段 3][...]
段 = [段头 33B][密文 len B][认证标记 16B]

全局头（50 B）

偏移长度字段说明
04MAGIC"VGS2"
41kid密钥派生类型（0x01 = Argon2id）
54mArgon2id 内存参数（KiB），当前 65536
94tArgon2id 迭代次数，当前 3
131pArgon2id 并行度，当前 1
1416salt随机盐
3012nonceGCM nonce（派生密钥时使用）
428reserve保留，当前全 0

段头（33 B）

偏移长度字段说明
01type段类型：0x01 = 数据段，0x02 = manifest 段
18seq段序号，从 1 开始连续递增
98len该段密文长度（不含 tag）
1712nonce本段独立 GCM nonce
294CRC32覆盖 type(1) + seq(8) + len(8) + nonce(12)，即前 29 字节，大端

段在文件中的占用长度 = 33 + len + 16（段头 + 密文 + tag）。

段 AAD（13 B）

AAD = "VGS2"(4) + 用途(1) + 段序号(8, 大端)
用途字节含义
0x00manifest 段
0x01数据段
  • 注意用途字节与段头的类型字节取值不同（段头：数据 0x01 / manifest 0x02）。
  • 序号进入 AAD → 段被重排、替换或拼接时认证立即失败。

数据段明文

数据段明文是一段 tar 流（可包含多个文件），其内部路径由 manifest 的 tar_path 指向。为控制段大小，写入时按目标段大小（默认 64 MiB）切分，因此一个段的 tar 流只承载该批文件。

manifest 段明文

manifest = 条目数(4, 大端)
         + 条目 × N
字段长度说明
name_len2条目名长度（UTF-8 字节数）
namename_len条目名（UTF-8）
is_dir1非 0 表示目录
size8原始大小（无符号）
mtime8修改时间（有符号 i64，Unix 秒）
seg8内容所在数据段的序号
tar_path_len2tar 内路径长度
tar_pathtar_path_len该条目在数据段 tar 流中的路径（UTF-8）

解码要求严格：长度为负/超限、UTF-8 非法、或末尾存在尾随字节，均判定为 manifest 损坏。

扫描与崩溃回退

  1. 扫描从偏移 50（全局头之后）开始，按段头依次前进，要求 seq 从 1 开始连续。
  2. 遇到以下任一情况即停止扫描，把余下内容视为尾部垃圾：段头 CRC 校验失败、段类型未知、seq 不连续、剩余长度不足以容纳段头 + tag、读取失败。
  3. 取扫描到的最后一份完整且认证通过的 manifest 段作为当前视图。
回退语义的边界（诚实说明） 该机制用于保障崩溃 / 断电场景：写段时先写占位段头，写入密文与 tag 后再回填段头，最后单次 fsync，因此中断只会留下被忽略的尾段。它不提供对"有能力回滚或整体替换文件"的攻击者的检测——此类场景请依赖文件系统快照或外部校验。

追加、删除与压缩

  • 新增：追加一个或多个数据段 + 一份新 manifest 段。
  • 删除 / 改名 / 移动：只追加一份新 manifest 段（不重写旧数据段）。
  • 压缩（GC）：全量重写，回收被隐藏的旧段；触发方式为手动，或自动（垃圾率 > 30% 且箱子 > 256 MB，或累计 32 份 manifest）。
  • 已知边界：删除后条目立刻从 manifest 消失，但物理旧段在压缩前仍留在文件中；持有箱子与口令的人理论上可从中恢复。追加式保存以此换取写入速度。

并行化的格式约束（v2.1 起）

写盘顺序 = 段序号顺序 段之间彼此独立（各自 nonce / AAD），因此加密与认证可以跨线程并行；但段序号必须与文件中的物理顺序一致，所以写盘必须按序号串行。实现这一约束时不得让步，否则上述崩溃回退语义失效。

兼容承诺

  1. 旧格式永远可解：VG\x01、VG\x02、VG\x03、VGS1、VGS2 的解码路径永久保留，不会因为版本升级被移除。
  2. 格式变更纪律：任何格式变更 = 新魔数 / 新版本号头 + 旧格式仍可解 + 测试向量入库。性能与实现优化不得改变既有布局语义（v2.1 的多段并行加密即属此类：格式未变）。
  3. 可独立实现：本规范不含任何未公开的编码细节，第三方可据此实现读取器。
  4. 测试向量：仓库内测试覆盖格式往返与篡改检测（段头 CRC 篡改、AAD 换序号、manifest 截断 / 尾随数据等），见 VaultGuard_rs/ 下的测试。
